# Functional Specification - Credify APIs Phone Lookup

## Objective

Enable phone-based personal data lookup through Credify APIs, with a complete operational flow that includes provider authentication, audit persistence, RabbitMQ queueing, real-time progress tracking, and a dedicated UI where the user submits a target phone number for processing.

## Scope

- Backend integration with Credify authentication endpoint (`POST /auth`)
- Backend integration with Credify phone lookup endpoint (`POST /pftelefone`)
- Persistence of lookup history and provider responses
- Queue-based processing for single and bulk phone lookups
- Real-time progress tracking for queued jobs
- Dedicated page for entering a phone number and publishing it to RabbitMQ

## Out of scope

- Browser-side direct calls to Credify
- Person-juridical (`PJ`) phone flows
- File-import UI for bulk submission in the first delivery
- Credit management dashboards or provider billing analytics

## User journeys

### Journey 1: Submit a single phone number from the UI

1. User navigates to the Credify phone lookup page.
2. User enters a Brazilian phone number.
3. User clicks `Consultar telefone`.
4. System validates and normalizes the number.
5. System creates a queue job with one item and publishes it to RabbitMQ.
6. UI immediately receives a `jobId` and initial `queued` status.
7. UI starts tracking progress in real time.
8. When processing finishes, UI displays the final status and returned person data or an explanatory empty/error state.

### Journey 2: Observe progress in real time

1. After enqueue, the page subscribes to the job channel.
2. User sees counters and status badges change from `queued` to `processing` to terminal state.
3. If the connection drops, the page reconnects and fetches the latest snapshot.
4. UI shows final outcome when the job completes.

### Journey 3: Review lookup history

1. User opens the history view or history tab.
2. System lists previous lookups with normalized phone, status, and timestamp.
3. User can inspect response details for each lookup.
4. User can identify whether the lookup succeeded, returned no data, or failed.

### Journey 4: Reuse the same backend flow for mass lookups

1. Another internal entry point submits multiple phone numbers.
2. System creates one job and multiple job items.
3. Every item is queued and processed independently.
4. Progress and completion use the same counters, storage, and real-time events used by the single-phone UI.

## Inputs

### Single-number enqueue request

- `phone`: string, required

### Bulk enqueue request

- `phones`: string[], required

### Internal provider request fields

- `IdConsulta`: generated by the backend per queue item
- `Ddd`: derived from normalized input
- `Telefone`: derived from normalized input without DDD
- `TipoPessoa`: fixed to `F`

## Outputs

### Enqueue response

- `jobId`
- `status`: `queued`
- `summary`:
  - `total`
  - `queued`
  - `processing`
  - `success`
  - `notFound`
  - `error`

### Job status response

- Job metadata
- Aggregate counters
- Item-level statuses
- Final provider-derived data when available

### Final lookup result

- Input phone metadata (`ddd`, normalized phone)
- Status (`success`, `not_found`, `error`)
- Response code from provider
- Returned person data such as CPF, name, address fields, and phone type when available

## Business rules

1. **Phone normalization**
   - Accept formatted or unformatted Brazilian phone input.
   - Store digits only in normalized fields.
   - Reject inputs that cannot produce a valid `DDD + phone` combination.

2. **Provider authentication**
   - The backend generates JWT using `ClientID` and `ClientSecret` stored in `.env`.
   - The token is reused until near expiration or until the provider rejects it.
   - HTTP communication with Credify must use backend `fetch` calls (no SDK dependency).

3. **Queue-first processing**
   - UI requests do not call Credify directly.
   - Every lookup is first persisted and then published to RabbitMQ.
   - Single lookup is treated as a job with one item.

4. **Status mapping**
   - Provider code `1` maps to `success`.
   - Provider code `2` maps to `not_found`.
   - Provider code `3` maps to `error`.
   - Transport/auth failures also map to `error` with internal error classification.

5. **Retries**
   - Transient errors may be retried up to a bounded limit.
   - Business `not_found` results are terminal and must not be retried.
   - Authentication rejection triggers one token refresh attempt before item failure.

6. **Persistence**
   - Every lookup item is persisted regardless of outcome.
   - Raw provider response is stored for later inspection.
   - Queue lifecycle transitions are persisted for progress tracking.

7. **Real-time updates**
   - Progress events are emitted after persistence succeeds.
   - Snapshot API remains the source-of-truth fallback.

8. **Privacy and safety**
   - Provider credentials must not appear in logs, events, or UI payloads.
   - Only lookup-relevant result data is exposed to the frontend.

## Non-functional requirements

- **Reliability:** queue processing must survive transient provider outages and worker restarts.
- **Traceability:** each job and lookup item must be auditable by timestamp and status.
- **Performance:** enqueue should return quickly without waiting for provider completion.
- **Scalability:** the same flow must support single-item and multi-item jobs.
- **Security:** provider credentials remain server-side and token refresh is centralized.
- **Resilience:** realtime disconnects must recover through snapshot reconciliation.

## Acceptance criteria

1. A dedicated page exists for Credify phone lookup enqueue.
2. The page validates and submits a target phone number.
3. Backend creates a job/item record and publishes it to RabbitMQ.
4. Worker authenticates with Credify and performs `pftelefone` lookup.
5. Lookup results are persisted with normalized input and raw provider payload.
6. UI can observe job progress in real time.
7. Status endpoint exposes aggregate and item-level progress.
8. History view lists previous Credify phone lookups.
9. Provider response code `2` is represented as a user-visible `not found` outcome, not as a transport failure.
10. Provider credentials are sourced from `.env` and never exposed to the browser.
11. Auth and phone lookup requests are executed with backend `fetch`.
